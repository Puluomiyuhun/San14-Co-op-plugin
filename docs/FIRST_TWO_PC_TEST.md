# 首轮双机测试：当前范围和剩余接点

2026-10-10。最新证据见 [HANDOFF](HANDOFF.md)。本文是验收目标，不是执行许可；不能用旧 PID、一次性 claim、过期产物或测试替身启动游戏。

## 首轮测什么

固定已支持版本、34号起点、A张鲁/B刘备、窗口或无边框。两台电脑各开一个真实游戏，连接同一房间；首先完成**同日开局快照＋一次正常推进后的旬末快照**，共两个检查点。B可以等待A校正，首轮不要求B独立推进战场。

具体顺序：A当前中旬自动保存 → 传给B并切换刘备 → B核验后正式回执 → 双方准备、命令封口 → A正常推进一旬 → A自动保存下旬档 → 同一个B进程加载并保持刘备 → 正式确认 → 两侧收尾和存档核对。

不新增内政/出征命令，不手工额外保存或读档；遇到需要选择的事件停止并记录。普通报告可按当轮通知关闭。先后两个检查点不是推进两旬：旧版文档的“连续推进两旬”保留为下一阶段目标，需要起始快照之外再有两个旬末，超出现两bank/两Save能力，不冒充当前已支持。

## 进入首轮双机前还要接什么

1. **明确的有限边界完成接口。** 当前实测加载提供User/Menu/Game局部检查和发布事务短暂停；人工不操作不是持续输入fence。旧强RemoteCompletion的verify_held不能传空函数或恒True。无新命令诊断须明确使用自己的有限观察合同，同时保留世界/身份/日期、一次性加载和断线不重试检查。
2. **两侧实际启动编排。** A在原生Prepare前绑定真实房间，再使用新等待控制；B保留同一reader、两bank、规则历史、TLS和私钥，实际加载结果接到上述完成接口。`a_native_turn_start.py`仍是本地诊断，新的B本地Session也不能单凭加载完成就开放下一期。需要补本机批准构建、fresh进程、正常收尾与终态证据的一致入口。
3. **两台电脑的真实配置和连通。** 各自确认游戏版本和本机产物，建立可达地址/端口、TLS指纹及独立adapter key，先验网络传输，再启动上述窄实机流程。另一电脑不能复制本机PID、内存地址或历史回执来放行。

这是三处接线/部署范围，不是三个等量任务或进度百分比。当前无现成的一键实机双机命令。纯网络诊断可独立准备，但网络成功不等于游戏端已经安装完成。

## 成功要保留的证据

- 两端本次进程身份和版本、源码及产物核验；同一A与同一B进程贯穿两个检查点。
- 两份本次A自动生成的文件，日期正确、字节一致、与房间和各自代次绑定。
- B实际加载退休、刘备身份及规划地图、声明的两表与日期投影核验；投影不是全世界逐字段证明。
- 第一次正式完成后才能Ready/推进，第二次正式完成后才能结束；诊断ACK不代替正式完成。
- 原入口/规则按实际阶段恢复、发布器和调试器正常退出、存档变动留证；不清claim、不重投未知加载、不卸载固定模块。

任何回复丢失、状态不符或native结果不明都保留终态，不能为了继续测试自动重做加载。用户正常退出后才能按已核对备份恢复测试触及的旧档。
