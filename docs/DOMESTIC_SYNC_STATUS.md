# 内政同步现状与可并行的离线工作

2026-10-08。核查基线为提交 `1fe16c487a5e862d4a3b9bf63ee6ee70acaef929`，主线程与两名 agent 分别检查了房间/日志/准备、命令类别、赏赐执行链。本次未访问游戏、Steam、当前存档或 UI，只做源码与既有证据核查，并运行便携协议检查。本文不新增游戏功能或实机放行。

**内政已有基础，但进展集中在赏赐；完整的“正常点击菜单 → A 接受并执行 → B 游戏更新 → 双方确认”还没有接通。** 最近主要开发的是旬末保存、连续加载和规则换代。内政线可以与这些工作并行推进。

## 赏赐究竟走到了哪里

历史实机证明了**一份游戏中的跨势力执行**：张鲁视角下替刘备赏赐固定三名武将，忠诚由 93/91/99 变为 97/95/100，金钱减少300，行动力10→9。历史网络实验使用两个本机 TCP/HMAC 进程；不是两个真实游戏，也不是现代 TLS 房间。报告明确另一客户端状态复制未实现。

当前各组件的边界如下：

| 组件 | 实际作用 | 不能据此宣称 |
| --- | --- | --- |
| `room_session.Room.binding_for_command` | 绑定认证玩家与势力，仅接受赏赐 schema | 已执行命令或已同步武将；回执只是 `BINDING_CHECK_ONLY` |
| `authority_reward.validate_reward` | 检查赏赐的归属、军团范围、资金来源、资格、日期和上下文 | 函数会调用游戏；它只返回预检结果 |
| `checkpoint_reward_owned_replay` | 构建自己的命令容器、重验身份，经过持有许可执行并清理 | 新实现已在实机跑过；24项是自有进程检查 |
| `checkpoint_planning_dispatcher` | 有排队、重读上下文和 owned replay 调用 | 已与最新 A 保存/输入 Owner 合并；旧18项是独立 DLL 组合 |
| `execution_journal` | 每副本持久化意图/结果、顺序、去重；结果未知时保持等待 | 自动捕获菜单、网络分配顺序或真实暂停游戏；这些需要适配器 |
| `authoritative_sync.PeriodCoordinator` | 接收已应用命令序号与摘要，双方一致且无在途命令才封住准备边界 | 自己执行了赏赐或验证了完整世界；当前输入来自可信外部适配器 |

最新 A Owner 交接明确说明：远端赏赐队列尚未合入；旧 Dispatcher 与它争用同一个 User 更新槽，不能叠装。下一步应复用队列和 owned replay 逻辑，形成一个拥有保存、规划命令及准备边界的后继 Owner。

因此用户问“A赏赐后B会不会立刻看到新忠诚度”，**目标如此，当前还不能承诺**。仍需 B 执行/应用、独立读取结果及 UI 刷新的证据；只收到网络包或看到 A 的结果不够。

## 最值得并行开发的工作包

这些是待交付工作，不是本次已完成的新功能。可分配不同 agent，先约定窄接口、各自修改后继文件，最后做组合验证。

| 优先级与工作包 | 不碰游戏可以交付什么 | 离线验收应覆盖什么 | 仍需实际游戏验证什么 |
| --- | --- | --- | --- |
| P0：当前唯一 A Owner 接赏赐队列 | 从已有 Dispatcher 拆出队列/执行逻辑，接现有保存/准备调度；复用 owned replay | 同一实际回调来源、连续两命令、保存与赏赐互斥、执行中准备、取消/异常/换世界拒绝、完整收尾 | 普通菜单接管与真实主线程行为、实际输入限制 |
| P0：现代房间到 A、再到 B 的赏赐流程 | TLS认证身份→A分配顺序→现有SQLite日志→执行端口→B独立进程消费→结果回执；本地A操作走同一顺序 | A/B同时提交、重复/乱序/旧旬请求、断线、执行后丢回执、两份日志状态及准备排空；执行用自有原生fixture并明确标注 | 两个持久游戏中的真正应用和另一端菜单刷新 |
| P1：命令能力清单和统一协议后继 | 复用已有房间/日志约束，分开提案、任务创建、已应用结果、失败；按命令类型登记版本、字段与阶段 | 未实现类型拒绝，错误势力/人物/日期/资源上下文拒绝，不允许客户端自行声明“已执行”；准备只接受已核对的应用回执 | 菜单原生拦截，支持清单与实际执行入口吻合 |
| P1：商人交易与武将移动适配准备 | 将 preview 转为严格语义命令；有界执行归档包装链，核对参数容器、对象寿命、资源扣除和任务创建顺序 | 特别检查移动不能漏扣行动力；缺字段、重复武将、资源变动、已占用人物、未知规则均不猜测放行 | 一次有针对性的菜单字段/资源结果对照及真实执行 |
| P2：施政或地区内政分配选一类深入 | 由现有类型与候选入口追到明确参数布局，新增一个 decoder 和完整作用范围说明 | 有效/损坏自有内存模型、对象归属、取消与重复分配；不同时给全部内政打“支持”标记 | 该类菜单与字段对应关系 |
| P2：延时任务和事件流程整合 | 将任务提交与任务完成分开，把已有事件暂停模型接房间/日志接口；准备事件所属玩家和选择回执 | 第5天/第7天、同日多个事件、只读通知、重复确认、断线、跨旬任务；随机结果以A权威为准，不能让B重复抽取后当作一致 | 真实原生事件出现位置、双方停在对应边界与继续执行 |

赏赐适合作为第一条带操作的验收线，因为它已有实际执行和资源结果证据。交易和移动可在协议/归档层并行准备。对未确认的内政规则，先记录未知点，不能发明价格、天数、行动消耗或成功率来让测试通过。

现有去重、日志、鉴权和准备逻辑值得直接复用；当前最缺的是**把这些组件与唯一原生执行入口接成同一条流程**，不需要从零重写另一套模拟联机框架。
