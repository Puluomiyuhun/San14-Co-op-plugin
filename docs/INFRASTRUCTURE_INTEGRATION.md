# 三条基建线如何合在一起

2026-10-10。用户本轮要求先并行推进基建，暂缓双机实测。所有本轮测试都不访问游戏、Steam 或当前存档；并行完成的组件不能简单相加为“双人玩法已经完成”。最终验证编号见 HANDOFF 顶部与公开证据。

## 当前装配方式

| 组件 | 本轮落地点 | 入口/对象占用 | 与现有链路的关系 |
| --- | --- | --- | --- |
| A 双人势力保护 | `a_protected_rules.py`、`a_protected_start.py` | 原六处 AI/收入入口 | 与 A 七处保存/父入口无重叠；同一 world 跨旬保留规则，正常结束先恢复规则再恢复保存入口 |
| A 带保护的网络入口 | `observed_protected_host.py` | 使用上述同一 A Runtime 和实际 TLS 房间 | 新明确配置，不修改冻结旧入口；仍只允许无新命令的开局快照＋一次旬末 |
| 赏赐真实上下文与结果核验 | `reward_observed_context.py`、`reward_observed_flow.py` | 不写新的原生入口 | 复用 GameReader、原资格/资金读取、原排序队列与双日志；本机执行仍由可信 Owner 适配器提供 |
| 按阶段限制玩家输入 | `player_input_policy`、`player_input_owner` | 独占本游戏窗口的 WndProc；调用现有赏赐 Owner | 不安装第二套 User/Save/AI 入口，不与旧窗口 boundary/resident 叠装 |

AI 六处入口：`C6660 / C65F0 / C6580 / C66A0 / 28DE71 / 28DAA5`。A 七处入口：`3F8606 / 3F9B16 / 13DC09 / 12CC4D0 / 12DC620 / 12CC9E0 / 1297D10`。地址不冲突只是必要条件，仍须核对实际 descriptor、原字节、进程和对象身份、在途调用及恢复结果。生产自动保存 Runtime 中的同一个 Owner 才能承担赏赐，不能另装一个旧赏赐 DLL 来“拼接”。

## 玩家准备与执行封口是两件事

一人点击准备，含义是“我不再下新命令”，不应阻止接收、执行另一人已经获准的命令。旧 `ReadyFence` 也拒绝远端赏赐，因此本轮输入策略不把一人准备映射成该开关。真正全体准备仍要等双方队列清空、结果一致，再建立保存/推进边界。

| 阶段 | 本地已审计游戏输入 | 远端消息 | 远端赏赐执行 |
| --- | --- | --- | --- |
| 内政、尚未准备 | 放行 | 可接收 | 经同一可信 Owner、身份和资源复核后执行 |
| 内政、本人已准备 | 拦截 | 可接收 | 仍可执行，不能因本人准备而丢掉对方操作 |
| 保存、加载、等待事件、推演 | 拦截 | 可接收并由上层保留 | 暂停执行 |
| 终态或未知结果 | 保持已能拦截的范围 | 本期停止接纳 | 不自动重试 |

阶段转换必须等实际窗口控制消息处理完后取得 ACK；准备开放输入不能只靠 Python 写一个布尔值。进入保存/加载等关键阶段前，还检查已有赏赐是否排队、执行中或结果未知，不能让它跨过阶段边界。

这个窗口拦截只覆盖已有审计证据的消息。绘制、计时和窗口生命周期继续运行；没有把所有 Enter/鼠标都当作“关闭报告”放行。普通报告与需要选择的事件尚未可靠区分，设备缓存、其他输入消费者和所有世界写入也未全覆盖。因此 `allInputHeld`、完整 Ready/保存授权始终不据此变为 true。

## 即时赏赐结果如何核对

A、B 各自保留自己的视角，本地重新读取两个人类势力的资金、军团行动力、相关武将忠诚/状态与任务等字段；比较摘要不包含本机地址或观察者势力等不应相等的内容。命令仍经过同一个 A 排序队列，A 本地命令也在其中。

每次执行前重读归属、资格和资源；执行后实际读取结果，核对每人100金、一次1行动力、被选中武将的忠诚及赏赐标记，并检查声明范围内其他字段未发生意外变化。忠诚增量采用实读值，不编造固定公式。A 完成后等待 B 独立执行并签名报告，再处理下一条；重复包不再次扣钱，执行后丢回复保留已应用日志，不自动重做。

这些是有限字段观察，不是完整世界原子快照。游戏日期、world、进程出生时间或本机 attachment 改变，旧适配器永久退休，不能把身份改回来就继续用旧命令。

## 还不能直接连起来的地方

1. **当前 A Runtime 的赏赐生产桥。** 需要从同一个 Runtime 导出可信的提交/报告及 Owner 引用，在实际串行执行时机接新结果核验；目前新赏赐测试的原生业务是明示替身。
2. **同一房间的规划周期。** 赏赐有限投影与存档房间的完整检查点合同不同。新赏赐局部服务明确拒绝把自己的 Ready/seal 当存档房间已经封口；需统一期次、队列排空和退休边界。
3. **实际窗口引导与菜单生命周期。** 输入 Owner 仍需从游戏 GUI 线程正确初始化、保证唯一发布者；赏赐确认前暂留、安全关闭和取消不能只用旧“弹出当前栈顶”的调用代替。
4. **加载/跨旬重绑定与事件。** 本轮 AI 支持同 world 推演；输入与赏赐对象不能跨 world 沿用。B 读档后需退休旧对象并为新 world 建立新绑定；延时任务中途弹出的选择仍待接。

下一轮应优先把同 Runtime 的赏赐生产桥与规划周期接好，再把窗口引导接到该唯一 Owner。双机地址、证书和整组游戏验证按用户安排后推，不要求用户反复手动复现所有内政。
