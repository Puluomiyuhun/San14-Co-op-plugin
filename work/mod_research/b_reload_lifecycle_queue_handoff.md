# 启动线程池接入与连续两次加载组合

2026-10-08。新后继将冻结的 `b_reload_lifecycle` 与完整
`b_reload_activated_queue` 链接进同一个自建进程。没有修改冻结生产源，没有运行
新进程游戏加载器、查找游戏、访问 Steam、当前存档或 UI。

## 实际接通的部分

此前启动生命周期只执行两个简单任务，完整加载队列则另有单线程构造替身。
本轮执行一次归档 `509580` 四线程初始化，由原生 `1447B6` 调用后的同一
生命周期桥登记四个尚处初始等待的 worker。之后同一个已暖 worker 连续处理
两代完整队列；第二代不重新建立线程池、不重新初始化 activation、不重置旧回执。

- 每个场景两次实际 queue pop/Finalize，三个嵌套 Load/Title 角色的 start/join。
- 16 个 Root 任务、48 次实际捕获；每份任务保持 generation 2 或 3 和原线程身份。
- 每代另有一项无授权票的普通任务透明执行，不产生 Provider 任务或改变其报告。
- `nested-input-yield` 场景两代各一次真实 Root yield、输入租约交接及 parent resume。
- 两个旧 observation window 完成后退休；新代不改变旧 Session/queue/Provider 报告。
- 四个已注册 worker 正常退出后各有外层 FINALLY，活动任务清理完成。

跨代保留的新增内存页是启动调用所在 `144000` 与四个 pool control 所在
`1A24000`；既有 runner/entry/IAT/updater 页沿用旧组合的保留方式。每次使用前
检查四个 control/object/thread/入口、IAT，以及一次且仅一次的启动桥结果。
这些是自有内存的测试生命周期，不是安装到游戏的发布器。

## 保留的失败

- `200518-114352-5b12ec`：4 个场景都在共享构造器服务冲突处失败。启动 fixture
  将 `833CB0` 改为 pool 构造替身，完整队列随后也通过同一个通用构造入口建立
  Load/Title worker，被错误算作第 5 个 pool worker。现在四线程初始化结束后恢复
  原有嵌入式 worker 的构造替身；没有更改归档调用者或生产身份检查。
- `200647-619943-aec45f`：两代加载过程均完成，但第二代普通 warmup 带入持久
  callable 的上一任务参数，且旧单世界测试把累计普通任务数固定为 1；yield 场景
  也误将两代总数写成 1。现在显式清零该次普通任务的三个参数、按代核对累计次数，
  yield 严格要求每代一次、共两次。未删除失败记录或放宽原生门槛。

## 仍不能据此声称的能力

构造器、callable 服务、业务写入和文件语义仍有明确替身。构造替身主动等待实际
线程进入初始等待；真实游戏构造器的时序仍未证明。第二份输入是诊断变体，
**不是 A 新生成的合法 SAN14 存档**。没有实机读档、世界全量验证、持续全输入/
写入排他、真实启动发布器、规则六入口换代或房间跨旬 Ready 放行。

新增组合消除了“启动来源和完整加载队列只各自通过”的离线接线缺口；不能把
4 个场景写成两个真实客户端或两份真实新档已通过。自动观察故障矩阵尚未与本组合
一起执行，沿用旧故障结果时必须明确其来源层次。

下一步仍需确认真实运行时字节可用且 pool 尚未启动的接入阶段、完成实际 Bootstrap/
来源发布，然后单游戏连续读取两份合法新档。A 新档生产与持久输入/执行排他是另外
两项门槛。没有待用户操作或新增游戏补丁/调试器。
