# Retained B local diagnostic session (2026-10-10)

This successor provides a concrete local factory and a retained two-load owner.
It does **not** provide a continuously held engine/input fence, a formal remote
completion adapter, or an end-to-end two-computer run. No game process, Steam
directory, UI or installed native publisher was accessed during this work.

## Implemented boundary and native composition

`b_remote_session_boundary.py` wraps the unchanged bounded stable sampler. Every
check requires two equal complete planning samples, the fixed PID/birth/image,
five native slot originals, mode zero, actual queue/task/current fields and all
existing pending-input checks. Only the predecessor's exact transient mismatch
may retry within its original bounds. A returned frozen `Observation` explicitly
sets input exclusion, scheduler fence and atomic snapshot to false. The human
no-new-command condition must be explicitly true. No `verify_held=True` adapter
or empty callback exists in these production files.

`b_remote_session_lifecycle.py` declares a **different constructor contract**
from the frozen strong-fence lifecycle. It reuses the original native rule
restore/load/observe/Prepare/Seal/install predicates and original bootstrap A→B
identity checks. Its callbacks perform repeated observations; they do not claim
execution stopped between those observations. Actual rules publication retains
the predecessor's brief debugger-held source transaction. Local `hold` means
terminal owner state, not a native pause. The frozen old lifecycle, capture,
bridge and formal protocol contracts were not edited.

The bridge invokes the existing native-refresh loader: backup exact old target,
independent received-source lease, no Python `files.apply`, actual native
FileWrite/readback and target lease, native completion, six-slot retirement,
then actual handover before bank 1. The expected planning viewer/date changes
only after the original complete refresh/retirement acceptance. Failed or
uncertain calls keep their objects and evidence and cannot replay.

## Concrete entry points

`Session.open(...)` in `b_remote_session.py` requires an actual `GameReader`,
authenticated B `RoomConnection`, immutable room scope/settings, known first
profile and generation-1 `NextWorldRequest`, exact target identity, fresh private
records, private adapter-key file, explicit approved pair/helper manifests and
hashes, production `RulesBuild`, Steam DLL paths and caller-approved source pins.
It verifies target name/scope before claims or native work. It then checks the
source and production-build closures, exact Steam DLL files, planning, original
rules, no debugger and prior process claim; creates an exclusive process claim;
constructs the actual stable `Resident`; and constructs the real diagnostic
`RemoteRulesWorldCapture`/`RulesFactory` successors. Prepare, Seal, publisher and
`ResidentPort` native methods are unchanged. The first A-view rules are installed
before constructing the retained bootstrap lifecycle/bridge. There is no default
PID, discovery, automatic game launch, inferred key, automatic key export or CLI
that executes on import.

`session.apply_native(received, request, profile, reservation=None)` validates
the typed TLS-received file and actual SQLite journal. First generation requires
the explicit source-view `BootstrapCheckpointJournal`; later input requires the
ordinary `CheckpointJournal`. A supplied reservation must already match the
locally persisted `INTENT`; no received dictionary creates permission. It
exclusively records a native intent, calls the actual bridge, applies the original
deep native/refresh acceptance, samples the complete declared object/force world
projection, and records local completion. The same reader, TLS connection,
Resident, lifecycle, bridge, boundary, factory and scope remain bound.

After successful first load, this session alone leaves the journal **STAGED**
(or its pre-existing INTENT), leaves the A period unchanged, sends no advisory or
formal ACK, and grants no Ready. After two loads its phase is
`TWO_LOADS_RETAINED`. The key is retained privately; status exposes only its
fingerprint. `open` failures attach `retained_session` to the primary exception;
logging failure cannot replace that exception. Native handles/modules/publishers
are not automatically closed, revoked, unloaded or terminated. The owner must
be retained for review/explicit cleanup. An unsuccessful local apply is terminal.
