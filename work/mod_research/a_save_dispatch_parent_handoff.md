# A 保存宿主：CApp 父边界与旁路

2026-10-09。全部离线，只读已有固定归档。没有访问游戏、Steam、UI、当前存档或进程，没有活动补丁/调试器和待用户操作。新增审计不安装宿主，不授予保存许可。

## 确定了什么

固定归档的 MSVC RTTI 把 `13D9C0..13DD03` 归于 `CApp` 虚表 `+10h`；pdata 边界吻合。函数内已有 B 父层桥使用的 `13DC09 call 509FE0`，返回点 `13DC0E`。因此 A 的候选控制入口可以复用这段已知调用来源设计，不需要把网络线程或 User 工作线程假定成控制线程。

新审计实际执行整个父函数的三条有界路径：

- 正常路径调用一次状态调度器，返回后继续 `3B5560` 等父层业务。
- `13C100` 的服务替身返回非零时，原生条件跳过调度器及其后部分处理，但仍执行公共尾部并正常返回。不能把每次 CApp 返回都算成一次 Game/User 完成观察。
- 开启对应父层标志时，实际控制流先调用 `13900`、`10860`，随后才到状态调度器。它们的业务全部是替身；不能把调度器入口之前的处理自动归入已覆盖输入范围。

三个路径都执行父层临界区服务的进入/退出调用和正常 epilogue。临界区是模型服务，**不是实际 Windows 锁或跨帧稳定线程证据**。源码身份/RTTI检查加三条执行路径合计4/4；不是四次游戏测试。

## 仍不能据此做什么

所有子函数，包括 `509FE0`，都是显式替身。本实验没有运行实际工作线程、证明子任务 FINALLY、排空后台writer、执行保存或取得完整输入覆盖。一个函数在同一仿真CPU上正常返回不证明真实每帧都来自同一Windows线程。已有 B 测试对 yield 的证明也不能直接变成 A 已完成观察。

候选宿主应在匹配的实际 `13DC09/13DC0E` 调用两端保留调用编号、App/manager、线程及返回来源；第一次初始化Controller后固定控制TID，后续错线程拒绝。父调用发生前有未完成/yield的子任务，或状态转换/对象身份变化时不得领取保存请求；父返回后仍需真实Owner/Gate所有回调收尾以及Controller完整观察。不要在实际User BEFORE/AFTER里重入Controller，也不要因为同一调用返回就放宽它的 `clean()`。

新的 `a_save_dispatch_mailbox` 负责请求跨线程转交；它不提供上述来源。下一步需要**单一所有者**把真实父桥和邮箱接上，同时补生产者/保存writer协调。A与B不能各自在相同call-site叠装独立桥。若需要实机观察，保留一次连续记录里的父call/return与实际任务收尾；明确验证跨帧TID与yield，不重复仅观察一次空闲手动保存。
