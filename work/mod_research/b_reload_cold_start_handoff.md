# B 冷启动：构造返回不能代替初始等待证据

2026-10-08。仅使用本机已有归档与冻结 CPU 模拟器；没有查找、启动或操作游戏、Steam、当前存档或 UI。无实际 OS 子线程、调试器、补丁或待用户操作。

## 新证据

`b_reload_cold_start_audit.py` 实际解释执行归档的 `509580` 四线程初始化循环、`833CB0` 控制对象构造及 `83A070` 线程工厂父链。两种显式服务模型各执行877条原生指令：

- 子线程全部延迟：原生请求四次 suspended creation、四次恢复，发布四个正确对象，初始化器返回成功；模型中尚无子线程执行。
- 服务模型标记子线程先到等待：同一父链仍正常返回。这个标记是模型假设，不是执行出来的子线程上下文。

分配器、空callable搬移、计数器/临界区创建、名称复制、cookie检查及线程/事件服务都是替身。没有模拟CRT内部、OS真实调度或实际worker代码。因此结果是**所审父链没有提供“返回时四线程已到初始wait”的保证**，不是证明实机已出现竞态、线程永不到wait或安装一定失败。

原生工厂在 `83A136` 请求带标志4的线程创建，`83A1DA` 调用恢复服务后直接取对象并返回。上层构造在返回前继续构造计数器和事件，没有读取本审计中的子线程到达状态。服务名称依相邻原生调用/参数及既有线程布局解释，OS实现未执行。本审计不把替身行为当作Windows实测。

## 对当前实现的影响

冻结 `b_reload_lifecycle.cpp::after` 直接调用 `RegisterColdPool`；后者每线程只做一次暂停/上下文展开，严格要求初始等待 `83A9D7`。自有四worker/queue fixture的构造替身会主动等子线程到达，因此可以隐藏这个生产时序缺口。不能用增加fixture等待或重复跑成功次数将其消除。

后继应在同一初始化生命周期、尚未派发普通任务的条件下，区分“尚未到初始等待”和来源/对象/事件错误。若实现有界等待，必须每轮恢复自己暂停的线程、保留真实上下文与原始入口校验、保证没有任务生产者提前发事件，并在截止或不确定时停止；不能重置旧RegisterColdPool认领后重试，也不能把已暖worker的 `834DFD` 当作初始等待。此策略**尚未实现或获实机验证**。真游戏归档来源何时就绪仍是另一个独立缺口。
