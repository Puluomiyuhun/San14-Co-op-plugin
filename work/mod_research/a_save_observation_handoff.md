# 一次正常保存的观察工具

2026-10-08。新观察器与启动脚本已通过 **34/34 自有进程及模型检查**，并经另一 agent 只读复审。本轮用户暂时不方便操作，**没有执行 `--preflight` 或 `--record`，没有访问游戏、Steam 或当前存档**。没有活动游戏调试器、游戏补丁或待用户操作请求。

用途是回答一个具体问题：正常保存的主要序列化区间内，army 后台更新是否仍有正在执行的已配对任务。它不发保存、读档、推进或游戏输入，也不提供保存许可。四点、字段及原生调查见 [事件契约](a_save_native_coordination_handoff.md)。

34 项分为：

- 9 项实际自建进程硬件断点检查：正常取样、超时、取消、错误 birth、生产版拒绝 fixture、已有断点拒绝、普通异常/INT3 转交、双线程排队事件及取样异常后的排队清理。

## 下次用户方便时才执行的步骤

先确认没有别的调试器/规则补丁，用户在受支持版本的34号基线张鲁大地图；不要根据历史 PID 或这篇文档假定当前状态。

```powershell
py -3 work/mod_research/a_save_observation.py --preflight
```

这个显式选项才会只读打开游戏；核对 EXE、PID/birth/base、203年8月中旬张鲁身份、五层规划状态、空闲阶段、原更新槽及 15 处小段原指令指纹。它不附加调试器，也不产生许可。检查不通过就停止，不能修改期望值绕过。

以**本机刚刚通过的测试目录**为 `--tested-build`，不要复制别的电脑的结果：

```powershell
py -3 work/mod_research/a_save_observation.py --record --tested-build "work/mod_research/a_save_observation_test_runs/<本机通过的时间戳>"
```

启动器先核对所有依赖源码及生产二进制摘要，再重新检查游戏身份。原生记录器重复检查后附加，收到 `READY_FOR_ONE_MANUAL_SAVE` 才通知用户正常保存到一个空白测试槽，避免覆盖34号档或旧档；返回大地图后不下令、不推进。工具不会替用户点保存，也不声称已验证目标文件名。

默认等待 1800 秒，可用 `--seconds` 指定 1–3600 秒。完整 Save 返回且已看到的 worker 返回后自动收尾。等待期间若用户取消，在本次输出的运行目录创建 `trace.jsonl.stop` 即可请求正常退出。不要强杀持有调试事件的记录器。

若出现 `cleanup_pending=true` 或恢复不确定记录，应保留该进程和日志，先处理退出问题，不读档、不推进、不启动第二个观察器。不确定时工具会保留调试器，不伪造恢复成功。

## 观察方式与结论边界

采用 Windows 调试接口及每线程四个硬件执行断点，不改原生代码字节或游戏业务数据。暂停事件取样会改变线程时序；因此这是观察实验，不能把它当成不扰动游戏的性能测量。

- Save `2F7C28 → 2F7C2D` 配对同线程、同 RSP、archive/stream。
- Army `16C1A0 → 16C2B7` 配对同线程、同 RSP、栈中实际返回地址及固定 manager。
- 记录带本次 PID/birth/base/run ID、连续 seq；已有和新建线程均纳入观察。
- 正常/错误/超时/取消均先恢复原六个调试寄存器并处理已排队的自有异常，再解除调试。若当前寄存器布局已由外部改变，则保留不确定状态，不覆盖外来布局。
- 清理时丢弃的已排队观察点、清理异常/进程退出、达到事件上限或计数不符，全部让分析结果变成不完整。最终损坏 JSON 不会被默默忽略。没有 Save 的干净超时为 `INCONCLUSIVE`。

没有观察到重叠不证明排他；观察到重叠也不证明同一字段发生数据竞争或存档损坏。附加前已进入、解除后才返回的 worker 可能不在窗口内。所有结果始终保持 `production_permit=false`、`full_world=false`，不会发布文件、解锁输入或 Ready。

下一步是取得一次实际正常保存的完整记录，再依据真实 Save/worker 顺序决定是否继续观察队列/原生 join 边界。`16C160` 含清理副作用，不能作为“仅等待后台结束”的捷径调用。这个工具本身不完成 A 两次新档生产或双人联机。
